# Основные концепции

Данный раздел является вводным и призван познакомить читателя с основными концепциями работы с библиотекой.

## Особенности проектирования

Библиотека представляет собой ядерную кроссплатформенную обёртку над WSK (Windows Socket Kernel) и Linux Socket Kernel. Два эпитета в её полном описании — «ядерная» и «кроссплатформенная» — играют ключевую роль и определяют основные архитектурные решения.

### Ядерность

Поскольку библиотека работает через системные вызовы (инкапсулируя работу с ними), она должна собираться соответствующим образом. При этом сборка под Linux и Windows выполняется принципиально по-разному. Эта проблема решается просто: создаётся единый файл, который включает в себя все `.c` файлы реализации. Выглядит это примерно так:

```c
#include "../src/adapters/linux/linux_adapter.c"
#include "../src/common/linux/linux_common.c"
#include "../src/common/linux/linux_common_release.c"
// ...
```

В зависимости от платформы вы либо компилируете проект в `.lib` файл (Windows), либо подключаете его через Makefile (Linux).

### Кроссплатформенность

Кроссплатформенность накладывает обязанность свести различное поведение платформенных функций к единому интерфейсу. И несколько раз приходилось искать компромиссы.

Например, Windows требует сложной инициализации — диспетчер функций для вызова системных вызовов WSK доступен не сразу. В то время как Linux предполагает, что все ядерные функции доступны мгновенно.

В связи с этим библиотека накладывает на пользователя определённые обязательства. Для сохранения единого интерфейса вызов некоторых функций на Linux формально не обязателен, но важен для поддержания кроссплатформенной структуры кода.

И, соответственно, из-за кроссплатформенности была разработана [особая архитектура](./../architecture.md), обеспечивающая её поддержку и возможность дальнейшего расширения.

## Паттерн работы с библиотекой

Общий паттерн работы с библиотекой включает следующую последовательность действий:

1. Подключение библиотеки

2. Инициализация библиотеки (`net_register()`)

3. Активация библиотеки в каждом рабочем потоке (`net_activate()`)

4. Вызов необходимых сетевых функций

5. Проверка статуса, возвращаемого каждой функцией

6. В зависимости от статуса — принятие решения: продолжить работу или выполнить аварийное завершение, закрыв все созданные сокеты

7. После завершения работы с библиотекой — вызов `net_cleanup()` для освобождения ресурсов

## Поддерживаемые функции

### Управление сокетами
- Создание и закрытие TCP/UDP сокетов
- Подключение к удалённым узлам (TCP-клиент)
- Ожидание входящих подключений (TCP-сервер)
- Привязка сокета к локальному адресу и порту

### Передача данных
- Отправка и приём данных по TCP
- Отправка и приём дейтаграмм по UDP
**Примечание**: в текущей версии библиотеки поддерживается только блокирующий режим работы с сокетами.

### Работа с адресами
- Гибкий подход — пользователь может как самостоятельно заполнить структуру `net_address_t`, так и использовать готовые функции парсинга
- Преобразование строковых адресов (`192.168.1.1:8080`, `[::1]:9001`) в структуры и обратно
- Поддержка IPv4 и IPv6, включая `link-local` адреса с `scope_id` (как числовыми, так и строковыми идентификаторами интерфейсов)

### Серверные возможности
- Создание слушающих TCP-сокетов
- Приём входящих подключений с получением адреса клиента
- Создание UDP-серверов с возможностью получения адреса отправителя

### Диагностика и обработка ошибок
- Единая система кодов ошибок для обеих платформ
- Сохранение оригинальных платформенных ошибок для глубокой отладки
- Доступ к последней ошибке сокета через специализированные функции

### Кроссплатформенность
- Единый API для Windows (WSK) и Linux (Linux Socket Kernel)
- Пользователь пишет код один раз — библиотека берет на себя платформенные различия

## Платформенное различие в поведении библиотеки

В процессе работы с сетевыми сокетами поток может находиться в блокирующем состоянии, ожидая входящих данных или подключения (net_socket_receive, net_socket_accept). При выгрузке драйвера или модуля возникает необходимость прервать эти блокирующие вызовы, чтобы поток мог корректно завершиться.

| Платформа | Механизм прерывания |
|-----------|---------------------|
| **Windows (WSK)** | Закрытие сокета (`WskCloseSocket`) принудительно завершает все ожидающие IRP, вызывая немедленный возврат блокирующей функции с ошибкой |
| **Linux** | `kernel_accept` / `kernel_recvmsg` не прерываются автоматически. Требуется разбудить поток через `kthread_stop` и дождаться его естественного выхода |

Для унификации поведения на обеих платформах желательно использовать глобальный контекст (как в туториалах),который:

* Хранит указатели на серверный и клиентский сокеты
* Содержит флаг should_stop для сигнализации потоку
* Доступен как из рабочего потока, так и из выгрузчика

### Пример подобного контекста 
```c
typedef struct {
    volatile int should_stop;
    net_socket_t* listen_sock;
    net_socket_t* client_sock;
} thread_context_t;

static thread_context_t g_ctx = {0, NULL, NULL};
```

### Пример реализации в выгрузчиках

#### Windows
```c
VOID DriverUnload(...) {
    g_ctx.should_stop = 1;
    if (g_ctx.listen_sock) net_socket_close(g_ctx.listen_sock);
    if (g_ctx.client_sock) net_socket_close(g_ctx.client_sock);
    KeWaitForSingleObject(g_WorkerThread, ...);

    net_cleanup();
}
```
#### Linux

```c
static void __exit module_exit(void) {
    g_ctx.should_stop = 1;
    if (g_WorkerThread) kthread_stop(g_WorkerThread);
    
    // Для унификации интерфейса, планируется
    // что очиста произойдет при пробуждении потока
    if (g_ctx.listen_sock) net_socket_close(g_ctx.listen_sock);
    if (g_ctx.client_sock) net_socket_close(g_ctx.client_sock);

    net_cleanup();
}
```

Несмотря на различия в механизмах, в обоих случаях очистка ресурсов происходит непосредственно в функциях выгрузки:

* Закрываются все созданные сокеты
* Освобождается память
* Вызывается `net_cleanup()`

При этом сам рабочий поток должен корректно реагировать на сигнал `should_stop` и завершаться естественным путём (возврат из функции потока). Принудительное завершение потока (`PsTerminateSystemThread` / `kthread_stop`) используется только как вспомогательный механизм.
